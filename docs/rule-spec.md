# Rule specification

Rules are TOML files. They describe known cache and disposable-data locations. They are **data, not code**: a rule cannot execute a command, open a network connection, or request privileges.

## Example

```toml
id = "xcode-derived-data"
name = "Xcode DerivedData"
description = "Build artifacts, indexes and logs generated by Xcode. Xcode recreates them on the next build."
os = ["macos"]
category = "developer"
risk = "safe"
recreate = "automatic"
paths = ["~/Library/Developer/Xcode/DerivedData/*"]
```

## Fields

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `id` | string | yes | Stable, unique, lowercase identifier. Use kebab-case. |
| `name` | string | yes | Human-readable name shown in the UI. |
| `description` | string | yes | Plain-language explanation of what the data is and what happens if it is removed. |
| `os` | array of strings | yes | `macos`, `windows`, `linux`. |
| `category` | string | yes | `developer`, `browser`, `system`, `trash`, `apps`, `media`, `other`. |
| `risk` | string | yes | `safe`, `low`, `medium`, `high`, `never`. |
| `recreate` | string | yes | `automatic`, `download`, `rebuild`, `manual`, `impossible`, `unknown`. |
| `paths` | array of strings | yes | One or more path patterns. |

## Risk levels

| Level | Meaning | Examples |
| --- | --- | --- |
| `safe` | Regenerated automatically, no user data. | Build caches, browser caches, package caches. |
| `low` | Re-downloadable or low impact. | Logs, thumbnails, old downloads. |
| `medium` | App state or archives that may matter. | Xcode Archives, app support data. |
| `high` | User data, device backups, containers, databases. | Trash, iOS backups, Docker disk image. |
| `never` | Must not be removed by Prune. | Documents, Photos library, keychains, system files. |

A future planner will use `risk` to decide what can be selected automatically. High-risk findings must always require explicit review.

## Re-creation values

| Value | Meaning |
| --- | --- |
| `automatic` | The app recreates it on demand without user action. |
| `download` | It can be downloaded again. |
| `rebuild` | It can be rebuilt from source or project files. |
| `manual` | Recreating it requires a manual step. |
| `impossible` | It cannot be recreated. Treat as high risk. |
| `unknown` | Not enough information; be conservative. |

## Path rules

v0.1 is deliberately strict:

- Paths must be inside the user's home directory.
  - `~/...` is expanded to the home directory.
  - An absolute path is accepted only if it is under the home directory.
- The path must be specific.
  - `~/Library/*` is rejected.
  - `~/Downloads/*` is rejected.
  - `~/Library/Caches/Homebrew/*` is accepted.
- No `.` or `..` components.
- No environment variables yet.
- Only literal path components and an optional final `/*` are supported.
  Recursive `**`, character classes, `?`, backslashes, padded components and
  platform device/root prefixes are rejected. This intentionally narrows the
  rule language to avoid ambiguous expansion.
- Unknown TOML fields are rejected. Risk labels remain declarations by rule
  authors, not independently verified permission to delete files.
- Discovery checks ancestors and rejects symlinks and Windows reparse points.
  These read-only checks do not eliminate concurrent filesystem replacement.
- No shell commands, scripts, or executable content in rules.

These checks are implemented in `prune_core::validate_path_pattern` and are covered by tests.

## Validation

```bash
prune rules validate
prune rules validate --rules-dir ./my-rules
prune rules list
prune rules list --json
```

Invalid rules fail the command with a non-zero exit code.

## Testing a rule

1. Run `prune rules validate`.
2. Run `prune scan --rules-dir ./my-rules --no-tui`.
3. Compare the reported size with `du -sh <path>`.
4. Confirm the path contains only regenerable data.
5. Add a fixture-based test if the rule is part of the built-in set.

## Review checklist

- [ ] The path is documented by the app vendor or verified on a real machine.
- [ ] The rule does not point at user documents, photos, keys, or credentials.
- [ ] The risk level is honest.
- [ ] The re-creation path is accurate.
- [ ] The description tells the user what will happen.
- [ ] The rule works on every OS it claims to support.
- [ ] The rule has no broad glob that could match unrelated data.
